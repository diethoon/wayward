# Wayward 공통 엔지니어링·검증 운영 표준

적용 범위: Wayward 관련 모든 저장소, 브랜치, 엔지니어, 자동화 작업 및 총괄참모의 독립 검증.
목적: 단순 작업시간 단축이 아니라 동일한 시간 안에 더 많은 요구사항을 정확하고 안전하게 완성하고, 검증 가능한 증거까지 확보한다.

## 1. 작업 착수 전 기준선 확정
- 저장소·대상 브랜치·최신 HEAD를 먼저 확인한다. 전달받은 SHA가 현재 HEAD와 다르면 차이를 확인하고 최신 기준으로 이어간다.
- HANDOFF, README, 관련 설계·계약 문서, 기존 구현, 테스트, CI, 최근 실패 로그와 산출물을 우선 조사한다.
- 이미 구현·검증된 부분은 재사용한다. 목적 없는 전체 재조사, 중복 구현, 동일 테스트의 무의미한 반복을 금지한다.
- 요구사항을 완료 가능한 단위로 분해하고, 각 단위의 선행조건·변경 범위·완료 증거·차단 요인을 착수 전에 정한다.
- 기존 사용자 데이터, API 계약, 인증·암호화·저장 형식, 배포 상태와 보호 경계를 명시한다.

## 2. 엔지니어의 실행 방법 최적화
- 가장 짧고 정확하며 되돌리기 쉬운 실행 경로를 선택한다. 코드를 작성하기 전에 문제 원인과 최소 변경 범위를 특정한다.
- 반복 가능한 탐색·변환·검사·빌드·패키징은 스크립트, 테스트 러너, CI로 자동화한다. 대량 수작업은 자동화가 부적절할 때만 수행한다.
- 기존 도구·테스트 fixture·로그·캐시·산출물을 재사용하고, 새 도구나 의존성은 실제 이점이 있을 때만 도입한다.
- 실패하면 처음부터 전체 과정을 반복하지 않는다. 실패 단계와 원인을 좁혀 해당 부분만 수정하고 필요한 검증을 재실행한다.
- 과도한 추상화, 목적 없는 리팩터링, 무관한 파일 변경, 중복 서비스·중복 테스트를 피한다.
- 진행 중 발견한 새로운 사실은 HANDOFF에 즉시 기록해 다음 담당자가 같은 조사를 반복하지 않게 한다.

## 3. 도구·플랫폼 선택
- 각 작업마다 사용 가능한 도구의 권한·기능·비용·속도·검증 가능성을 비교해 가장 적합한 수단을 선택한다. 특정 플랫폼을 습관적으로 사용하지 않는다.
- Git/GitHub는 브랜치·커밋·diff·리뷰·이슈·Actions·아티팩트 추적에 활용한다.
- GitHub Actions 및 적절한 CI는 반복 테스트, 빌드, 패키징, 체크섬, 릴리스 후보 검증에 활용한다.
- Vercel은 웹 프런트엔드·서버리스·웹 배포 및 해당 플랫폼에 적합한 앱 작업에 활용한다.
- Render는 상시 서비스·백엔드·지원 데이터 서비스 작업에 활용한다.
- Cloudflare는 DNS·네트워크·보안·Workers·스토리지 등 해당 기능에 적합한 작업에 활용한다.
- 로컬 스크립트·테스트·빌드 도구와 연결된 플랫폼 기능을 비교해 중복 실행을 줄인다.
- 도구의 연결·권한·리소스·실행 결과를 실제로 확인한다. 사용 불가능한 권한이나 존재가 확인되지 않은 API를 가정하지 않는다.
- 외부 플랫폼을 추가할 때는 기존 구조보다 나은 이유, 운영 비용, 장애 지점, 중복 여부를 먼저 판단한다.

## 4. 병렬화와 의존성 관리
- 독립적인 조사·코드 변경·테스트·문서 작업은 안전한 범위에서 병렬 처리한다.
- 공통 파일, 동일 브랜치, 공유 API, 순차적 데이터 변경처럼 충돌 가능성이 있는 작업은 소유자를 정하거나 순서를 조정한다.
- 선행조건이 있는 작업만 순차 처리한다. 병렬화로 통합·충돌 해결 비용이 커지면 병렬화하지 않는다.
- 각 병렬 작업에는 입력 기준선, 수정 허용 범위, 산출물, 검증 방법을 명시한다.
- 작업 종료 시 결과를 통합하고 통합 상태에서 필요한 회귀 테스트를 수행한다.

## 5. 테스트와 증거 수집
- 변경 범위에 맞는 가장 빠른 단위 검사부터 실행하고, 통합 테스트·전체 테스트·CI 순으로 확대한다.
- 이미 동일 코드·동일 환경에서 통과한 검증은 재사용할 수 있으나, 관련 코드·환경·의존성이 바뀌면 필요한 검증을 다시 실행한다.
- 테스트 명령, 종료 코드, 테스트 수, 실패 로그, CI 실행 링크, Job 결과, artifact ID, 체크섬을 기록한다.
- Mock, fixture, 정적 분석, 단위 테스트, 에뮬레이터, 실제 기기, 실제 외부 서비스 검증을 구분한다.
- Mock 성공은 실제 OAuth·Drive·GPU·네트워크·기기 성공을 의미하지 않는다. 미실행 항목은 미검증으로 명시한다.
- 패키지는 실제 산출물 존재 여부, 파일 구성, 버전, 체크섬 및 가능한 경우 재현성을 확인한다.

## 6. 총괄참모의 독립 검증 의무
- 엔지니어의 완료 보고를 그대로 승인 근거로 사용하지 않는다.
- 보고된 시작/최종 HEAD, 브랜치, 커밋, 변경 파일을 GitHub에서 독립 확인한다.
- diff를 직접 확인해 요구사항과 변경 범위가 일치하는지, 무관한 변경·보안 회귀·기존 기능 삭제가 없는지 검사한다.
- 핵심 구현과 API 계약을 직접 읽고, 테스트가 실제 요구사항을 검증하는지 확인한다. 단순히 테스트 이름이나 성공 문구만 믿지 않는다.
- CI 실행의 대상 SHA, 모든 필수 Job 상태, 실패/취소/생략 Job, artifact의 실제 존재를 확인한다.
- 가능한 경우 테스트나 빌드를 별도로 재실행하거나 결과를 교차 확인한다. 재실행하지 않았다면 그 사실을 명시한다.
- 패키지·APK·ZIP·체크섬은 artifact 메타데이터와 실제 다운로드/검사 결과를 구분해 보고한다.
- 실제 계정·기기·서비스 검증이 불가능하면 자동 검증 완료와 실환경 미검증을 분리해 판정한다.
- 요구사항별로 완료·부분 완료·미완료·차단 상태를 독립적으로 판정하고 근거를 연결한다.

## 7. 보안·데이터·권한 경계
- 속도 때문에 인증·인가·암호화·개인정보·데이터 무결성·백업 호환성·회귀 검증을 생략하지 않는다.
- 사용자의 기존 데이터, 모델, LoRA, 워크플로, 설정, 세이브를 임의로 변경하거나 삭제하지 않는다.
- 승인 없는 병합, 배포, 릴리스, 삭제, 권한 변경, 운영 설정 변경, 외부 공개를 하지 않는다.
- API·엔드포인트·토큰 흐름·플랫폼 권한은 실제 구현 또는 공식 계약으로 확인한다. 추측으로 만들어 연결하지 않는다.
- 문제 해결을 위해 보안 경계를 약화하거나 인증·TLS·CORS를 우회하지 않는다.

## 8. 보고와 인수인계
- 간결하게 시작 기준선, 최종 기준선, 수행 내용, 변경 파일, 테스트/CI 증거, 산출물, 미검증 항목, 차단 요인을 보고한다.
- 모든 주요 완료 주장에는 재현 가능한 증거를 연결한다.
- HANDOFF는 의미 있는 변경·검증 단계마다 갱신하고 현재 HEAD와 문서가 서로 모순되지 않게 유지한다.
- 다음 담당자가 같은 조사·실험을 반복하지 않도록 결정 이유, 실패한 시도, 남은 작업, 다음 실행 명령을 기록한다.
- 문서상 계획·제안과 실제 구현·배포·검증 완료를 명확히 구분한다.

## 9. 최종 완료 판정
작업 완료는 코드 작성이나 CI 녹색 표시 하나로 판정하지 않는다. 요구사항 충족, 기존 기능 보존, 변경 범위 적정성, 자동 검증, 필요한 실환경 검증, 산출물 확인을 종합한다.
최종 원칙: **가장 적합한 도구로 불필요한 단계를 줄이고, 독립 작업은 병렬화하며, 자동화로 반복을 제거하고, 총괄참모가 코드·diff·테스트·CI·산출물을 독립 검증한다.**
