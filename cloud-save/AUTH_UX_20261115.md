## Adapter decision and flow

| Environment | Adapter | Expected behavior |
|---|---|---|
| Android/native launcher exposing the `WMLHost` marker | `android-native` fixed at setup even if auth methods are absent | native-only dispatch; missing API fails closed; forced account selection requires `startGoogleDriveAuthWithPolicy`; nonce-scoped result retrieval; no GIS fallback |
| HTTPS / allowed localhost | `browser-gis` fixed at setup | GIS `requestAccessToken` called synchronously from game-button click; no auth-061 popup |
| PC `file://` | `file-unsupported` fixed at setup | explicit fail-closed error; no launcher, Host, local port, remote auth page, CORS relaxation, opaque-Origin trust, or wildcard message transport |

`forceSelectAccount` never chooses or changes the transport. First connection and explicit logout set it to `true`; if the native policy API is missing, CloudSave returns an explicit unsupported error instead of silently using the legacy method or browser GIS.

## HTTP / HTTPS direct GIS

- Load GIS during CloudSave setup for the `browser-gis` adapter, before the user clicks.
- The game-button handler calls `initTokenClient` and `requestAccessToken` without awaiting or opening another page first. GIS manages the authorization popup.
- On explicit logout, `prompt: 'select_account'` is passed. Otherwise the remembered-account/first-consent behavior uses `prompt: ''`.
- The callback requires a returned `state` identical to the per-attempt nonce, verifies current auth attempt and session generation, and checks the granted `drive.appdata` scope before applying the token.
- Popup-closed and popup-failed-to-open errors are surfaced in the game UI. Token remains in page memory only.
- Direct GIS requires a compliant JavaScript origin. Google requires HTTPS except localhost/loopback HTTP; the exact game origin also has to be configured in the OAuth Web Client. The known Vercel game origin is `https://wayward-six.vercel.app`, but its Google Console registration could not be inspected.

## PC file:// constraint and server-free decision

- file:// is an opaque origin (serialized as null); it is not an authorized JavaScript web origin for GIS. The web Token Model requires a registered secure JavaScript origin; it does not authorize arbitrary local file origins.
- Google's official Desktop App OAuth flow uses Authorization Code + PKCE, but the system browser redirects to a loopback URI and the desktop app must listen on that local port. A listener is a local server dependency and is expressly excluded by the current CloudSave architecture requirement.
- Google's TV / Limited-Input Device OAuth flow does allow the drive.appdata scope, but Google documents it for limited-input devices and requires the user to visit a verification URL on a separate, richer-input device and enter a user code. That is not the required one-click PC browser flow. The documented device-code and token endpoints are client HTTP endpoints; Google does not document them as CORS-enabled browser APIs. Reports of the exact device-code endpoint from browsers show missing CORS response headers, so a file page cannot rely on reading those JSON responses.
- Google's legacy OAuth authorization endpoint itself does not support CORS for JavaScript fetch/XHR; its documented browser pattern uses navigation/form submission, which cannot return the authorization response to an opaque file origin securely.
- A hosted static auth page or Cloudflare/Vercel/Pages relay would add a fixed external origin dependency; a local listener would add a local server dependency; a browser extension/native app would add an installed component. None satisfies the current requirement that a plain PC file:// game with only a browser, Internet and Google account authenticate without launcher, server, extension or external auth relay.
- Runtime behavior is therefore deliberately fail-closed: file-unsupported returns a specific in-game error. It does not silently fall back to GIS, use Origin:null as a trust boundary, open an external auth page, relax CORS, send credentials through postMessage('*'), or contact localhost.
- PC file:// Google Drive authentication remains technically blocked under the stated constraints. No official one-click, browser-only, no-server flow was found. Completion requires changing a platform constraint (e.g. an installed first-party native OAuth handler or serving the game from a registered HTTPS web origin); those alternatives are not enabled by this work.

## 2026-11-16 — server and launcher independence decision (supersedes earlier Host bridge proposal)

### Governing architecture

CloudSave must not depend on Wayward PC Launcher, Remote Host, ImageGen, ComfyUI, any local server, a Wayward backend, a resident PC/mobile service, or a fixed auth relay URL. The previous Host-owned Desktop OAuth + loopback listener design is rejected because it contradicts this higher-priority rule.

### Current adapters after the change

- HTTPS / allowed localhost: the existing direct GIS Token Model stays in CloudSave. The game button invokes GIS synchronously; tokens remain in game memory and Drive API calls go directly from the module to Google.
- Android: the existing window.WMLHost native adapter remains fixed when that marker exists. Missing methods fail closed; there is no GIS fallback. This is the existing optional platform-native authentication integration, not a server or Remote Host dependency.
- PC file://: the obsolete hosted bridge and its revoke popup were removed from mod.js. The adapter now returns an explicit unsupported error without attempting any network endpoint or local port. This is not a claim that PC file authentication is complete.

### Why a pure file-browser OAuth implementation is unavailable

1. Browser GIS Token Model: requires a registered HTTPS JavaScript origin (localhost/loopback HTTP is the development exception). A raw file:// page has an opaque origin and cannot be registered as a web JavaScript origin.
2. Desktop App OAuth: officially uses Authorization Code + PKCE with the system browser and a loopback callback listener. A listener is a local server, forbidden by the governing architecture.
3. TV / Limited-Input Device OAuth: it supports Drive appData, but the Google UX requires a separate richer-input device to enter a user code. It is not the Windows browser's full-input desktop flow, and browser JavaScript cannot assume CORS access to the device-code/token endpoints.
4. Web Authorization Code flow: the code callback/token exchange is designed around a registered web origin and authorization-code endpoint/backend. A hosted static or dynamic callback would create the fixed external-origin dependency that this requirement rejects.

Google policy links:
- Desktop apps: https://developers.google.com/identity/protocols/oauth2/native-app
- Browser JavaScript origins / GIS: https://developers.google.com/identity/protocols/oauth2/javascript-implicit-flow
- Limited-input device flow and supported Drive scopes: https://developers.google.com/identity/protocols/oauth2/limited-input-device
- Google documents the browser OAuth authorization endpoint as not CORS-enabled: https://developers.google.com/identity/protocols/oauth2/javascript-implicit-flow
- Browser reports for the device-code endpoint also show no CORS headers: https://stackoverflow.com/questions/43144941/how-do-i-do-google-oauth-from-a-local-html-file-with-the-file-protocol-with

- Changed: cloud-save/mod.js removes the Pages auth-061.html URL/Origin constants, opener popup protocol, file bridge adapter route, and remote revoke popup. The file adapter now fails closed with a specific Korean explanation.
